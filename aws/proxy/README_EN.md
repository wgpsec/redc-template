# Multi-Node Proxy Scenario

## Scene Description

This scenario deploys multiple Shadowsocks-based proxy nodes in AWS ap-east-1. By default it creates 10 t4g.nano spot instances, making it suitable for quickly getting a batch of proxy exits that can be consumed together.

After deployment, you get the node public IP list, batch SSH commands, and a Clash configuration generated by plugins. If R2 upload is configured, the generated configuration can also be uploaded automatically for distribution.

## Prerequisites

- You need working AWS credentials and the ap-east-1 (Hong Kong) region enabled.
- This template uses ARM64 instances, so the target account must be able to launch the required instance type in that region.
- The scenario uses spot instances by default, so node availability and final node count can be affected by capacity.
- If you want automatic R2 upload, install and configure `rclone` first and prepare a Cloudflare R2 bucket.
- If R2 upload is not configured, the scene still works; you just need to use the locally generated Clash configuration file instead.

## Quick Start

```bash
redc pull aws/proxy
redc run aws/proxy
redc run aws/proxy -e node=10
redc status [uuid]
redc stop [uuid]
```

The default deployment creates 10 nodes. Override the node count with `-e node=...` when needed.

## Parameters

| Parameter | Required | Default | Example | Behavior Impact |
|-----------|----------|---------|---------|-----------------|
| `node` | No | `10` | `20` | Controls how many proxy nodes are created. More nodes increase both cost and available exits. |
| `port` | No | `60001` | `60010` | Controls the Shadowsocks server port and affects the generated Clash configuration. |
| `password` | No | `O9E3b1/OdxCrLkTmWyTL7w==` | `StrongProxyPass123` | Controls the proxy authentication password and also affects the generated config file. |
| `filename` | No | `aws-config.yaml` | `team-proxy.yaml` | Controls the generated Clash configuration file name locally or after upload. |
| `buckets_name` | No | `test` | `proxy-config` | Used only when R2 upload is enabled; defines the destination bucket name. |
| `buckets_path` | No | `/proxyfile/` | `/shared/aws/` | Used only when R2 upload is enabled; defines the upload path prefix. |

## Outputs

When deployment outputs drive your next step, focus on these items first:

- `public_ip` / `ecs_ip`: Public IP list of all proxy nodes, useful for checking whether the full node set is up.
- `ssh_commands`: Batch SSH commands for logging into each node and checking service status.
- Clash configuration file: Generated by `redc-plugin-clash-config` from `port`, `password`, and `filename`; if R2 upload is configured, the upload plugin can distribute it further.

## FAQ

- If R2 upload is not configured, the scene still works. Use the locally generated Clash configuration file directly.
- If startup fails, check these items first:
	1. Whether the AWS API connection timed out.
	2. Whether ap-east-1 still has spot instance capacity.
	3. Whether the AMI architecture matches the selected instance type.
	4. Whether the `rclone` configuration is correct.
	5. Whether the R2 bucket name or path settings are consistent.

## Appendix

- In the redc execution path, the Clash configuration is generated by `redc-plugin-clash-config`, and the R2 upload is handled by `redc-plugin-upload-r2`; the `upload_to_r2` function in `deploy.sh` is more relevant for standalone Terraform usage.
- If you want to enable R2 upload, install and configure `rclone` first:
	- https://github.com/rclone/rclone/releases
	- https://dash.cloudflare.com/ r2

![](../../img/redc-1.png)

```text
rclone config
s3
Cloudflare R2 Storage
xxxxxxxxxxxxx
xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
https://xxxxxxxxxxxxxxxxxx.r2.cloudflarestorage.com
auto

rclone lsf r2:test
```

- If you use `deploy.sh` in standalone mode, you can also adjust the generated download URL in its `upload_to_r2` function, for example:

```text
echo "url : https://your-r2-address-here/proxyfile/aws-config.yaml"
```
